1. What the lab is, and why

Homa is a datacenter transport protocol designed by John Ousterhout's group at Stanford as an alternative to TCP for remote procedure calls. Its claim is low tail latency for short messages under load — 10 to 100 times lower than TCP in their measurements — obtained by being message-based instead of byte-stream based, by letting receivers schedule incoming traffic, and by using the priority queues already present in datacenter switches.

Homa is implemented as an out-of-tree Linux kernel module, PlatformLab/HomaModule. Upstreaming into the Linux kernel started in October 2024 and proceeds in stages; it is not in a mainline release yet. This lab tests that module.

What this lab is for. Behaviour and correctness, not performance. The hosts are KVM guests on a single 12-core machine, so absolute latencies and throughputs are not datacenter numbers. What the lab can show honestly is: the build works and passes its own tests; Homa works end to end over IPv4 and IPv6; what it puts on the wire; how it compares on the same machines with TCP; what priority queues do for it under incast; how it recovers from loss; and how its defaults behave on a slower network than it was tuned for.
  • Pinned and reproducible. The kernel version and the HomaModule commit are fixed in lab.conf; one command builds the image from nothing, compiles the module and runs its 840 unit tests.
  • A switch that matters. Homa depends on switch priority queues. sw1 is a Linux VM whose ports implement exactly what Homa's documentation asks of a top-of-rack switch: strict priority queues selected by the top three bits of DSCP. They can be swapped for a single FIFO to see the difference.
  • Measured with Homa's own tools. homa_test, the echo server and cp_node come from HomaModule's util/; the lab adds orchestration (tools/homalab.py), a packet dissector, and Robot Framework suites that turn each experiment into checks.

2. Homa for dummies

No networking background needed. If you already know how TCP works, skip to section 3.

The problem: computers in a datacenter talk in small requests

When you load a web page, search, or open an app, the service behind it is not one computer. One request fans out to dozens or hundreds of servers, each asked a small question ("what's in this user's cart?", "give me result 7 to 12"), and the page is ready only when the slowest answer arrives. So what matters is not the average speed of a message but the speed of the unlucky ones: the 99th percentile, the tail. If 1 message in 100 is slow and a page needs 100 of them, most pages are slow.

Almost all of these messages are tiny — a few hundred bytes — mixed with occasional big transfers (a file, a backup, a model). The problem is the mix: the tiny messages get stuck behind the big ones.

What TCP does, in one paragraph

TCP, the protocol nearly everything uses, was designed in the 1970s–80s for the internet. It opens a connection between two computers (a phone call), then sends an endless stream of bytes down it, in order. It doesn't know where one message ends and the next begins. Each sender guesses how fast it may go by speeding up until packets get lost, then backing off. The network's queues fill up before anyone slows down, and a small message that arrives behind a big transfer waits its turn in the queue.

An analogy. TCP is a single-lane road where every truck driver accelerates until there is a crash, then brakes. A pizza scooter that happens to be behind a convoy of trucks waits behind all of them.

Homa is a loading dock with a dispatcher. Small parcels may drive straight in, in an express lane. Anyone with a truckload phones ahead; the dispatcher, who sees everything heading for the dock, tells each truck when to come — the one with the least left to unload goes first. Nobody crashes into a queue to find out it is full, and the scooter never waits behind a truck.

How Homa works, in five ideas

1
Messages, not streams. You send a whole message and the other side receives a whole message. A request plus its answer is a remote procedure call (RPC) — exactly what datacenter software does all day.
2
No connections. No call to set up and hang up. One Homa socket can talk to thousands of other machines with no per-machine setup, where TCP needs a separate connection to each.
3
Small messages just go. A message up to about 40 KB is sent immediately, without asking — a short request is done in one trip. A longer message is announced instead, and waits for the receiver.
4
The receiver is the dispatcher. For anything longer, the receiver sends grants ("send me the next 10 KB now"). The receiver is where traffic piles up when many machines answer at once (incast), and it is the only one that sees all of it, so it is the right one to decide. It favours the message that is closest to finishing, which minimises average waiting.
5
The network's express lanes. Datacenter switches already have up to 8 priority queues per port, mostly unused. Homa stamps each packet with a priority: short messages and control packets in the fastest lane, big transfers in the slow lanes. A small message overtakes the queue instead of waiting in it.

Lost packets are handled without connections: the receiver notices a missing piece and asks for it again (a RESEND).

The benefits

  • Much lower tail latency for short messages under load. The Homa papers report 10–100× lower 99th-percentile latency than TCP for short messages in heavily loaded datacenter networks. This lab sees the same effect on a small scale: under incast, Homa's 100-byte messages stayed under 2 ms at the 99th percentile while TCP's took 20–40 ms (section 11).
  • No head-of-line blocking. In a TCP stream, one lost or slow message holds up every message behind it on that connection. Homa's messages are independent.
  • Incast handled by design. When 100 servers answer one client at the same moment, TCP's queues overflow; Homa's receiver lets them in a few at a time.
  • Scales to many peers. No connection per pair of machines means no connection storms, no connection tables, no handshakes before the first byte.
  • It fits what applications actually do. RPC frameworks build request/response on top of TCP's byte stream and have to re-find message boundaries; Homa gives them messages directly.
  • It uses hardware that is already there. The priority queues exist in today's switches; Homa needs them configured, not replaced.

The drawbacks

  • Not in Linux yet. It is an out-of-tree kernel module, tied to particular kernel versions (this lab pins 6.17.8 for that reason). Getting it into the mainline kernel has been under way since 2024, in stages, and the first upstream version will be deliberately incomplete.
  • Applications must change. It is not a drop-in replacement: the API is message-based, receive buffers are memory the application maps, messages are limited to 1 MB. Libraries help (there is gRPC support from the same group), but nothing using TCP works over Homa unchanged.
  • Datacenter only. It assumes a fast, low-latency, trusted network that one organisation controls, with congestion mostly at the receiver's link. It is not a protocol for the internet: there is no encryption, and NAT, firewalls, load balancers and cloud security groups that do not know IP protocol 146 will drop or mangle it.
  • It needs the switches configured. Without priority queues, much of the advantage for short messages is gone — this lab measured it: one FIFO queue made Homa's short-message latency about 10× worse at the median and 4× at the 99th percentile (section 11).
  • Hardware offloads are built for TCP. Network cards cut big TCP sends into packets in hardware; they don't do it for Homa. Homa works around this by disguising its packets as TCP ("TCP hijacking"), which some network security gear rejects — and which failed for large messages in this lab. Here TCP was faster for big transfers (section 10).
  • Big messages can be starved. "Closest to finishing goes first" is great for small messages and hard on huge ones while small traffic keeps arriving. Homa has a knob that reserves bandwidth for the oldest message (grant_fifo_fraction); it is off by default in this build.
  • Tuned for very fast networks. Its timers assume 25–100 Gbit/s. On this lab's 1 Gbit/s links, the defaults caused false "packet lost" alarms and failed requests under load until the timers were scaled (section 13).
  • A young ecosystem. Fewer tools, fewer people who know it, fewer production deployments. Even the project's own Wireshark dissector was out of date (this lab ships its own).

For anything crossing the internet, for bulk transfers, or where applications can't be changed, TCP (or QUIC) remains the answer.

3. Homa in five minutes

Messages, not streams

A Homa socket sends and receives whole messages: a request and its response form an RPC, identified by an id the client chooses (even numbers; the server answers with the id's low bit set). There are no connections — no handshake, no per-peer state to set up or tear down — and one socket can talk to any number of peers. Messages are limited to 1 MB (HOMA_MAX_MESSAGE_LENGTH). Applications use sendmsg/recvmsg on a SOCK_DGRAM socket with protocol 146; received messages land in a buffer region the application has mapped, so the kernel never copies them twice.

The receiver schedules

TCP's senders probe for bandwidth and back off when the network drops or marks packets; queues build up first. Homa inverts this. A message no longer than unsched_bytes (40,000 here, about one round trip's worth) is sent unscheduled, straight away. A longer one is scheduled: it waits for GRANT packets from the receiver, which knows every message heading its way and decides which to let in, and how fast. (Homa as published, and this module until September 2026, also sent the first unsched_bytes of a long message unscheduled; now a long message only announces itself with START_MSG and every byte is granted — section 8 shows it.) Because the receiver's downlink is where incast congestion happens, the receiver is in the best position to manage it.

SRPT, implemented with switch priorities

The receiver grants by shortest remaining processing time: the message closest to completion goes first. To make that real in the network, every Homa packet carries a priority (0–7, written into the top three bits of the IPv4 DSCP / IPv6 traffic class), and switches serve higher priorities first:

  • Unscheduled packets (whole short messages) use the top priorities, chosen by message length through unsched_cutoffs (the shortest get the highest).
  • Scheduled packets use the priority the GRANT names — the top scheduled priority (max_sched_prio, 6 here) for the message nearest completion, lower ones for the others.
  • Overcommitment: the receiver grants several messages at once (up to max_overcommit) so its link never idles when one sender stalls; the priorities keep them from hurting each other.

A short message therefore jumps over the queued bulk data at the congested switch port. That is the property section 11 measures.

Reliability without connections

The receiver tracks which byte ranges of each message have arrived. If a granted range does not arrive within resend_ticks milliseconds, it sends a RESEND; a sender that has nothing to send yet answers BUSY. The client's request is acknowledged implicitly by the response; servers learn that their responses arrived through ACKs (piggybacked on later traffic, or prompted with NEED_ACK). An RPC with no sign of life for timeout_ticks fails with ETIMEDOUT.

5. How the image is built

./lab.sh image (tools/build_image.sh) turns the Ubuntu 26.04 cloud image into images/homa-base.qcow2; every node is a copy-on-write overlay on it. A throw-away builder VM on libvirt's NAT network (the lab networks have no internet) runs image/homa-build.sh once and powers off:

1
Disable unattended upgrades and hold the kernel packages — the lab must not change under its tests.
2
Install the four mainline 6.17.8 packages (image, modules, headers) and make GRUB boot it by name; the distribution kernel stays installed as a fallback.
3
Clone HomaModule, check out the pinned commit, make against the 6.17.8 headers, install homa.ko into /lib/modules/6.17.8-061708-generic/updates/, build util/ (cp_node, homa_test, server, homa_prio, …) into /usr/local/bin.
4
Build and run the module's unit tests — a user-space harness that compiles the module's sources against mocks of the kernel (840 tests). Two definitions are needed for the Ubuntu headers (section 17). The result is kept in /var/log/homa-unit.result and checked by suite 01.
5
Install the lab's pieces: sw-qos, the systemd units for homa_prio and the test servers, the Homa dissector for tshark. Generalise the disk (machine-id, SSH host keys, cloud-init state).

Each node then boots with its own cloud-init seed: addresses, the lab user with your SSH key, /etc/hosts (h1–h4, and node1–node4, the names cp_node expects), homa in modules-load.d, the Homa sysctls, and the services; sw1 gets its bridge and sw-qos policy instead.

6. Getting started

./lab.sh image        # once, ~10 min: builder VM → images/homa-base.qcow2
./lab.sh up           # define the networks and VMs, start them
./lab.sh wait         # until SSH answers and cloud-init is done (~1 min)
./lab.sh verify       # kernel + module, sw1 policy, jumbo pings, a Homa RTT between every pair
./lab.sh test         # all Robot suites (~12 min) → results/<timestamp>/report.html
./lab.sh down         # shut the VMs down (5 VMs, 9 GiB RAM, 10 vCPUs while running)

Log in with ./lab.sh ssh h1 (user lab, password lab, and your SSH key), or the serial console with ./lab.sh console h1. ./lab.sh exec hosts '<command>' runs a command on all four hosts in parallel. The Lab Hub (port 8088) shows the lab's VMs and can power it.

Everything is measured from the host. tools/homalab.py is the single place that drives experiments: it reads lab.sh inventory, runs Homa's tools over SSH (every remote command carries its own timeout), reads sw1's queue counters and Homa's kernel metrics, and prints JSON. lab.sh bench, the Robot suites and this document all use it.

9. Walkthrough C — sw1's priority queues

Each of sw1's ports carries this tree, built by sw-qos apply prio 1gbit 200 (Appendix B): an HTB class limits the port to 1 Gbit/s — the bottleneck — and feeds a prio qdisc with 8 bands, each a 200-packet FIFO. Flower filters pick the band from the top three bits of the IPv4 TOS / IPv6 traffic class: Homa priority 7 → band 10:1, served first; priority 0 → 10:8. Anything unclassified (ARP, neighbour discovery) goes to the last band.

13. Walkthrough G — the resend timers

The incast runs in priority mode showed sw1 dropping thousands of packets that FIFO mode never dropped, and Homa logging RPC timeouts, with no loss injected. The per-band counters located it: the drops were in the lowest bands. The mechanism:

1
Two senders push 500 KB messages at h1. SRPT grants the message nearest completion at the top scheduled priority and parks the others at lower priorities (overcommitment).
2
Strict priority serves the top band first. At 1 Gbit/s a 500 KB message takes 4 ms to drain, and the next one starts behind it — so the parked messages' packets sit in the low bands for tens of milliseconds.
3
Homa's receiver hears nothing from them for resend_ticks = 5 ms and sends RESEND. The data is not lost — only queued — but the sender sends it again, into the same starved band.
4
The band overflows (sw1 drops), real gaps appear, more RESENDs follow; some RPCs exhaust timeout_ticks and fail.

Homa's defaults assume a 25–100 Gbit/s network, where the same bytes drain 25–100 times faster and a 5 ms silence really means loss. Scaling the timers by ten for this 1 Gbit/s network removes the effect (lab.sh homa sysctl resend_ticks=50 resend_interval=20 timeout_ticks=1000):

16. Findings

  1. Priority queues do what Homa's design says. With h1's port saturated, Homa's short messages keep near-idle latency when the switch has strict priority queues, and lose an order of magnitude without them. TCP cannot use the queues at all (section 11).
  2. Homa's timers are tuned for 25–100 Gbit/s. At 1 Gbit/s, SRPT plus strict priority starves parked messages longer than resend_ticks; the spurious retransmissions overflow the switch and RPCs time out. Timers scaled ×10 remove it (section 13). Anyone running Homa on slower links (or emulating it) should scale resend_ticks, resend_interval and timeout_ticks with the link speed.
  3. Light load: Homa's short-message tail is about 0.6× TCP's, medians are similar, TCP wins long messages thanks to TSO (section 10).
  4. Offloads: max_gso_size=100000 makes 1 MB RPCs time out here — consistent with the module's own note that GSO is temporarily broken. With hijack_tcp=1 small RPCs work (p50 141 µs, the same as without it), but 1 MB RPCs time out. The defaults (hijack_tcp=0, max_gso_size=1000) are kept; not investigated further.
  5. The unit tests do not compile against Ubuntu's mainline headers as shipped; with two definitions they all pass (section 17).
  6. Module lifecycle is clean: it refuses to unload while sockets are open, unloads without residue, and is loaded again automatically by the first protocol-146 socket.
  7. A malformed request lingers by design. A message shorter than the echo protocol's 8-byte header leaves the server waiting for a reply length it never gets; the client RESENDs, the server answers BUSY, indefinitely, until the client exits. Correct protocol behaviour — the server is "busy" — but a reason every lab command carries a timeout.

17. Lessons learned building it

The host was dropping the lab's packets

The first version linked the VMs with QEMU UDP-socket tunnels, as the other labs do. Homa ran, but with thousands of RESENDs and dozens of timeouts and no loss anywhere in the lab — sw1's counters showed no drops, the hosts' interfaces showed no errors. The host's UdpRcvbufErrors counter rose by 1,641 during one 100-RPC run: QEMU's socket backend leaves the host's default 208 KB receive buffer, about 23 jumbo frames, and Homa's bursts overflowed it. Raising net.core.rmem_default would have needed root and changed every lab on the host; isolated libvirt bridges fixed it locally and, as a bonus, gave the virtio NICs TSO. 1 MB each way went from 25.8 ms to 15.4 ms (line rate).

The unit tests and the distribution headers

HomaModule's unit-test harness compiles the module's sources in user space against the kernel headers with mocks. Against the Ubuntu mainline 6.17.8 headers it fails twice: the headers enable the __seg_gs per-CPU address space, which mock.h's plain current_task declaration conflicts with; and they turn preempt_count_add/sub into macros, which mock.c defines as functions. The build adds a header (test/lab-kconfig.h) included after kconfig.h:

#undef CONFIG_USE_X86_SEG_SUPPORT
#undef CONFIG_CC_HAS_NAMED_AS
#define CONFIG_TRACE_PREEMPT_TOGGLE 1

— presumably matching the author's own kernel configuration. With it, 840 of 840 pass.

Measure the network, not the application

The first incast runs showed TCP probes faster than Homa's. Two artefacts: the probes went to the same single-threaded cp_node server as the bulk messages, so they waited in the application; and two senders at ~0.4 Gbit/s each (on the old links) never filled a 1 Gbit/s port, so no queue formed at sw1 at all — the priority queues had nothing to do. Separate probe servers and a port that is actually oversubscribed fixed both. Likewise, running the 48 round-trip tests concurrently produced 27 ms latencies and timeouts — the 2-vCPU hosts were overloaded; one at a time they take 0.2 ms.

A switch port sees wire-size frames

With TSO on the hosts, sw1's virtio NICs received TCP's 64 KB segments as single "packets" (rx-gro-hw), so a 200-packet queue held 12 MB of TCP and the counters were meaningless. sw-qos turns off GRO, GSO, TSO and rx-gro-hw on sw1's ports so the host segments before delivering.

Capture where nothing has consumed the packets yet

The first traces, taken on h1, showed requests leaving but no responses or GRANTs arriving — yet the RPCs completed. Homa's GRO handler processes many arriving packets itself, ahead of the normal receive path where tcpdump taps: on h1, gro_grant_bypasses was 24,666 of 35,304 received GRANTs, and gro_data_bypasses about a fifth of the DATA. The lab captures on sw1 instead. (The dissector also had to use the packet's reported length, not the captured one, to show segment sizes from a 128-byte snaplen.)

tshark and AppArmor

Ubuntu's AppArmor profile for tshark does not let it read files in /tmp or a home directory, nor load plugins from ~/.local — it fails with "permission denied" on a file it plainly can read. The lab pipes captures in (sudo cat x.pcap | tshark -r -) and installs the dissector in the global plugin directory.

Appendix B — sw-qos

#!/bin/bash
# sw1's egress policy on its host ports: what a datacenter top-of-rack switch does to Homa's packets.
#   sw-qos apply prio|fifo|off [RATE] [LIMIT] [PORT..]   prio: htb RATE -> prio, 8 strict bands chosen by the top 3 bits of
#                                                        DSCP / IPv6 traffic class (Homa priority 7 = first band), LIMIT
#                                                        packets each; fifo: htb RATE -> one queue of 8 x LIMIT; off: no shaping
#   sw-qos loss PORT N|off        drop 1 out of N packets leaving PORT (clsact egress, gact netrand), any protocol
#   sw-qos show [PORT..]          the qdiscs, per-band counters (sent / dropped / backlog) and the loss filter
#   sw-qos stats [PORT..]         one JSON object: per port, per Homa priority, packets / bytes / drops
set -euo pipefail
PORTS_ALL=(eth1 eth2 eth3 eth4)
die() { echo "sw-qos: $*" >&2; exit 1; }
ports() { [[ $# -gt 0 ]] && echo "$*" || echo "${PORTS_ALL[*]}"; }

apply_port() {   # port mode rate limit
  local p="$1" mode="$2" rate="$3" limit="$4" prio band
  # queue wire-size frames, as a switch port sees them: no GRO, and no 64 KB virtio receive aggregates (rx-gro-hw)
  ethtool -K "$p" gro off gso off tso off rx-gro-hw off >/dev/null 2>&1 || true
  tc qdisc del dev "$p" root 2>/dev/null || true
  case "$mode" in
    off) ;;
    fifo)
      tc qdisc add dev "$p" root handle 1: htb default 1
      tc class add dev "$p" parent 1: classid 1:1 htb rate "$rate" ceil "$rate" quantum 9014 burst 90k cburst 90k
      tc qdisc add dev "$p" parent 1:1 handle 10: pfifo limit $(( limit * 8 )) ;;
    prio)
      tc qdisc add dev "$p" root handle 1: htb default 1
      tc class add dev "$p" parent 1: classid 1:1 htb rate "$rate" ceil "$rate" quantum 9014 burst 90k cburst 90k
      # strict priority: band 10:1 is served first. Unclassified traffic (ARP, ND) -> the lowest band via the priomap.
      tc qdisc add dev "$p" parent 1:1 handle 10: prio bands 8 priomap 7 7 7 7 7 7 7 7 7 7 7 7 7 7 7 7
      for prio in 7 6 5 4 3 2 1 0; do
        band=$(( 8 - prio ))                                      # Homa priority 7 -> 10:1 ... priority 0 -> 10:8
        tc filter add dev "$p" parent 10: protocol ip   prio 1 flower ip_tos "$(( prio << 5 ))/0xe0" classid "10:$band"
        tc filter add dev "$p" parent 10: protocol ipv6 prio 2 flower ip_tos "$(( prio << 5 ))/0xe0" classid "10:$band"
        tc qdisc add dev "$p" parent "10:$band" handle "$(( 20 + band )):" pfifo limit "$limit"
      done ;;
    *) die "mode must be prio, fifo or off" ;;
  esac
}

cmd_apply() {
  local mode="${1:?mode}" rate="${2:-1gbit}" limit="${3:-200}"; shift 3 2>/dev/null || shift $#
  local p; for p in $(ports "$@"); do apply_port "$p" "$mode" "$rate" "$limit"; done
  printf 'SW_QOS_MODE=%s\nSW_QOS_RATE=%s\nSW_QOS_LIMIT=%s\n' "$mode" "$rate" "$limit" > /run/sw-qos.state
  echo "sw-qos: $mode rate=$rate limit=$limit on $(ports "$@")"
}

cmd_loss() {
  local p="${1:?port}" n="${2:?N or off}"
  tc qdisc add dev "$p" clsact 2>/dev/null || true
  tc filter del dev "$p" egress 2>/dev/null || true
  [[ "$n" == off ]] && { echo "sw-qos: no loss on $p"; return; }
  [[ "$n" =~ ^[0-9]+$ && "$n" -ge 2 ]] || die "N must be an integer >= 2 (drop 1 out of N)"
  tc filter add dev "$p" egress matchall action gact pass random netrand drop "$n"
  echo "sw-qos: dropping 1/$n of the packets leaving $p"
}

cmd_show() {
  local p; [[ -f /run/sw-qos.state ]] && cat /run/sw-qos.state
  for p in $(ports "$@"); do echo "== $p"; tc -s qdisc show dev "$p"; tc -s filter show dev "$p" egress 2>/dev/null | grep -E 'gact|random|Sent' || true; done
}

cmd_stats() {   # parse `tc -s -j qdisc` into {port: {mode, prio: {7: {...}, ...}, total: {...}}}
  python3 - "$(ports "$@")" <<'PY'
import json, subprocess, sys
out = {}
for port in sys.argv[1].split():
    q = json.loads(subprocess.run(["tc", "-s", "-j", "qdisc", "show", "dev", port], capture_output=True, text=True).stdout or "[]")
    bands, total = {}, None
    for e in q:
        h, parent = e.get("handle", ""), e.get("parent", "")
        st = {"packets": e.get("packets", 0), "bytes": e.get("bytes", 0), "drops": e.get("drops", 0), "backlog": e.get("backlog", 0), "qlen": e.get("qlen", 0)}
        if e.get("kind") == "pfifo" and parent.startswith("10:"):
            band = int(parent.split(":")[1], 16)
            bands[str(8 - band)] = st
        if e.get("kind") in ("htb", "pfifo_fast", "fq_codel", "noqueue", "mq") and h == "1:" or (e.get("root") and total is None):
            total = st
    mode = "prio" if bands else ("fifo" if any(e.get("kind") == "pfifo" for e in q) else "off")
    out[port] = {"mode": mode, "prio": bands, "total": total}
print(json.dumps(out))
PY
}

sub="${1:-show}"; shift || true
case "$sub" in
  apply) cmd_apply "$@" ;;
  loss)  cmd_loss "$@" ;;
  show)  cmd_show "$@" ;;
  stats) cmd_stats "$@" ;;
  *) die "usage: sw-qos apply prio|fifo|off [RATE] [LIMIT] [PORT..] | loss PORT N|off | show [PORT..] | stats [PORT..]" ;;
esac
